## Part 1: Mutex [30 Points]

### Analysis: What Causes Entries to Get Lost?

**Short Answer:**

An entry is "lost" when a key-value pair is successfully inserted into the hash table by one thread, but another thread later tries to retrieve that same key and gets `NULL`, indicating the key was not found - even though it was previously inserted.

**Root Cause: Race Conditions**

The original code has **critical sections** in `insert()` and `retrieve()` that are not protected, leading to race conditions when multiple threads access the same bucket simultaneously.

#### Race Condition in `insert()`:

```c
void insert(int key, int val) {
  int i = key % NUM_BUCKETS;
  bucket_entry *e = (bucket_entry *) malloc(sizeof(bucket_entry));
  e->next = table[i];        // READ: Read current head of bucket
  e->key = key;
  e->val = val;
  table[i] = e;              // WRITE: Update bucket head
}
```

**The Problem:**
1. Thread A reads `table[i]` (e.g., gets pointer to entry X)
2. Thread B reads `table[i]` (also gets pointer to entry X) 
3. Thread A sets `e->next = table[i]` and `table[i] = e` (inserts entry A)
4. Thread B sets `e->next = table[i]` and `table[i] = e` (inserts entry B, overwriting A)
5. **Result:** Entry A is lost! It's no longer reachable from `table[i]`

This is a classic **lost update** problem. The operation `table[i] = e` is not atomic - it consists of reading the current value, computing the new value, and writing the new value. When two threads do this simultaneously, one write can overwrite the other.

#### Race Condition in `retrieve()`:

While traversing the linked list, if another thread is simultaneously inserting into the same bucket, the reader might see an inconsistent state or miss newly inserted entries.

**Why Multiple Threads Make It Worse:**
- Only 5 buckets for 100,000 keys means high contention
- Multiple threads frequently hash to the same bucket
- Probability of simultaneous access increases with thread count
- More threads = more lost keys

### Implementation: `parallel_mutex.c`

The solution uses a single global mutex (`pthread_mutex_t table_lock`) to protect all critical sections:

- `insert()` locks before reading/writing `table[i]`
- `retrieve()` locks before traversing the bucket
- Ensures atomic read-modify-write operations
- Guarantees correctness: **0 keys lost**

The graph shows:
- **X-axis**: Number of threads (1, 2, 4, 8, 16)
- **Y-axis**: Total time (insert + retrieve) in seconds

  - Original (incorrect) - faster but loses keys
  - Mutex (correct) - slower but guarantees correctness

### Time Overhead Estimate

**Estimated overhead: 2-4x slower** depending on thread count and contention.

**Factors contributing to overhead:**
1. **Lock acquisition/release**: System calls add latency (~50-200 nanoseconds per lock/unlock)
2. **Contention**: Threads waiting for locks when accessing same buckets
3. **Serialization**: Operations that could be parallel are now serialized
4. **Context switching**: Blocked threads need rescheduling

**Overhead by thread count:**
- 1 thread: ~1.5-2x overhead (minimal contention)
- 4 threads: ~2-3x overhead (moderate contention)
- 8+ threads: ~3-4x overhead (high contention)

**Explanation:** The trade-off is clear: **correctness requires synchronization overhead**, but this is necessary to prevent data loss. The mutex ensures that only one thread can modify the hash table at a time, preventing race conditions but reducing parallelism.

## Part 2: Spinlock [30 Points]

### Hypothesis: What Will Happen When Replacing Mutexes with Spinlocks?

**Short Answer:**

I expect that **spinlocks will perform similarly or slightly better than mutexes** for this hash table workload, but the difference will be relatively small (5-15% improvement at most).

**Reasoning:**

#### Key Differences Between Mutexes and Spinlocks:

**Mutex Behavior:**
- **Blocks the thread** when the lock is unavailable
- Thread is put to sleep and removed from CPU scheduling
- Requires **context switch** to wake up when lock becomes available
- Lower CPU usage (threads sleep while waiting)
- Better for **long critical sections** or high contention

**Spinlock Behavior:**
- **Busy-waits** (spins) when the lock is unavailable
- Thread continuously checks the lock status in a loop
- **No context switch** - thread keeps running on CPU
- Higher CPU usage (wastes CPU cycles spinning)
- Better for **very short critical sections** with low contention

#### Why Spinlocks Might Be Better Here:

1. **Critical sections are SHORT**: 
   - `insert()`: Just a few pointer assignments (microseconds)
   - `retrieve()`: Traversing a linked list (relatively fast)
   - These operations complete very quickly

2. **Lock hold time is minimal**:
   - If lock is held for < 1-2 microseconds, spinning is faster than sleeping
   - Context switch overhead (~1-10 microseconds) is avoided

3. **Moderate contention**:
   - 5 buckets with multiple threads
   - Some contention, but locks are released quickly

#### Potential Issues:

- **High CPU usage**: Threads consume CPU while spinning
- **Cache line bouncing**: Multiple threads spinning on same lock cause cache invalidation
- **With very high contention**: Mutexes might actually perform better

**Conclusion:** I expect spinlocks to be **slightly faster (5-15%)** than mutexes for this workload due to the short critical sections, but the difference will be modest. If contention is very high, mutexes might actually perform better because they don't waste CPU cycles spinning.

### Implementation: `parallel_spin.c`

The implementation replaces all mutex operations with spinlock operations:
- `pthread_mutex_t` → `pthread_spinlock_t`
- `pthread_mutex_init()` → `pthread_spin_init()`
- `pthread_mutex_lock()` → `pthread_spin_lock()`
- `pthread_mutex_unlock()` → `pthread_spin_unlock()`
- `pthread_mutex_destroy()` → `pthread_spin_destroy()`

**Note:** `pthread_spinlock_t` is Linux-specific and not available on macOS. This code will compile and run on Linux systems.

The graph shows:
- **X-axis**: Number of threads (1, 2, 4, 8, 16)
- **Y-axis**: Total time (insert + retrieve) in seconds
- **Three lines**:
  - Original (incorrect) - fastest but loses keys
  - Mutex (correct) - slower but guarantees correctness
  - Spinlock (correct) - similar or slightly faster than mutex

### Time Overhead Estimate

**Estimated spinlock overhead: 2-4x slower than original**, similar to mutex overhead.

**Factors contributing to overhead:**

1. **Lock acquisition/release**: 
   - Spinlocks use atomic operations (compare-and-swap)
   - Faster than mutex system calls, but still has overhead
   - **Estimated: 50-200 nanoseconds per lock/unlock**

2. **Busy-waiting**:
   - Threads spin in a loop when lock is unavailable
   - Wastes CPU cycles but avoids context switch overhead
   - **Estimated: 0-10 microseconds per wait** (depends on lock hold time)

3. **Cache effects**:
   - Multiple threads spinning on same lock cause cache line bouncing
   - Each thread invalidates the cache line when checking the lock
   - **Estimated: Additional 10-50% overhead with high contention**

4. **Serialization**:
   - Operations that could be parallel are now serialized
   - Same as mutex - necessary for correctness

**Overhead breakdown:**

**Compared to original (incorrect) version:**
- **1 thread**: ~1.5-2x overhead (minimal contention, no spinning)
- **4 threads**: ~2-3x overhead (moderate contention, some spinning)
- **8+ threads**: ~3-4x overhead (high contention, significant spinning and cache effects)

**Compared to mutex version:**
- **1-4 threads**: 5-15% faster (no context switch overhead)
- **8+ threads**: Similar or 0-10% slower (cache line bouncing dominates)

**Explanation:** While spinlocks avoid context switch overhead, they introduce CPU waste, cache contention, and memory bandwidth usage. For this workload with moderate contention, these factors roughly balance out, making spinlock overhead similar to mutex overhead. Spinlocks may provide a small performance benefit (5-15%) over mutexes for this workload due to short critical sections, but the difference is modest and may disappear or reverse with very high contention.

## Part 3: Mutex, Retrieve Parallelization [20 Points]

### Do We Need a Lock for Retrieval?

**Short Answer:**

**Yes, we need synchronization for retrieval**, but we can optimize it using **read-write locks** instead of regular mutexes to allow multiple concurrent retrievals while still protecting against concurrent modifications.

**Detailed Explanation:**

#### Why We Need Synchronization:

1. **Read-Write Race Conditions**:
   - If thread A is reading (traversing the linked list) while thread B is inserting into the same bucket
   - Thread B modifies `table[i]` to point to a new entry
   - Thread A might see an inconsistent state or miss newly inserted entries
   - Without synchronization, there's no guarantee of memory visibility between threads

2. **Memory Visibility**:
   - Without synchronization, there's no guarantee that writes by one thread are visible to reads by another thread
   - The compiler or CPU might reorder operations
   - Cache coherency issues might cause stale reads

3. **Pointer Safety**:
   - While traversing a linked list, if another thread modifies the list structure, we need to ensure we're reading valid pointers
   - In our implementation, inserts only add to the head, so existing nodes remain valid, but we still need to ensure we see the updated head pointer

#### Why We Can Optimize:

1. **Multiple Readers Can Coexist**:
   - Multiple threads can safely read the same data simultaneously
   - As long as no thread is modifying, concurrent reads are safe
   - This is the classic "multiple readers, single writer" pattern

2. **Read-Only Operations**:
   - `retrieve()` only reads data, it doesn't modify anything
   - Multiple `retrieve()` operations on the same bucket can run concurrently
   - We only need to prevent a `retrieve()` from running while an `insert()` is modifying the same bucket

#### The Solution: Read-Write Locks

Instead of a regular mutex (which allows only one thread at a time), we use:
- **Read locks**: Multiple threads can hold read locks simultaneously
- **Write locks**: Only one thread can hold a write lock, and it's exclusive with all read locks

This allows:
- Multiple `retrieve()` operations to run in parallel (all use read locks)
- `insert()` operations to be exclusive (use write locks)
- Better performance when there are many readers and few writers

### Changes Made: `parallel_mutex_opt.c`

The optimized version replaces regular mutexes with read-write locks to allow parallel retrievals.

#### Specific Changes:

1. **Lock Type**: Changed from `pthread_mutex_t` to `pthread_rwlock_t`
2. **Insert Function**: Uses `pthread_rwlock_wrlock()` for exclusive write access
3. **Retrieve Function**: Uses `pthread_rwlock_rdlock()` for shared read access
4. **Initialization**: Changed from `pthread_mutex_init()` to `pthread_rwlock_init()`
5. **Cleanup**: Changed from `pthread_mutex_destroy()` to `pthread_rwlock_destroy()`

#### Code Changes:

**Before (parallel_mutex.c):**
```c
pthread_mutex_t table_lock;

void insert(...) {
    pthread_mutex_lock(&table_lock);
    // modify table
    pthread_mutex_unlock(&table_lock);
}

void retrieve(...) {
    pthread_mutex_lock(&table_lock);
    // read from table
    pthread_mutex_unlock(&table_lock);
}
```

**After (parallel_mutex_opt.c):**
```c
pthread_rwlock_t bucket_locks[NUM_BUCKETS];

void insert(...) {
    pthread_rwlock_wrlock(&bucket_locks[i]);  // Write lock (exclusive)
    // modify table
    pthread_rwlock_unlock(&bucket_locks[i]);
}

void retrieve(...) {
    pthread_rwlock_rdlock(&bucket_locks[i]);  // Read lock (shared)
    // read from table
    pthread_rwlock_unlock(&bucket_locks[i]);
}
```

#### How It Works:

1. **Multiple Read Locks**: Multiple threads can simultaneously hold read locks on the same bucket, allowing concurrent retrievals
2. **Exclusive Write Lock**: Only one thread can hold a write lock, and it blocks all readers and other writers
3. **Per-Bucket Locks**: Each bucket has its own read-write lock, allowing parallelism across different buckets

#### Performance Benefits:

- **Parallel Retrievals**: Multiple threads can retrieve from the same bucket simultaneously
- **Better Scalability**: Retrieve performance improves with more threads
- **Read-Heavy Optimization**: Especially beneficial when there are many more reads than writes

#### Correctness:

- **No Lost Keys**: Write locks ensure inserts are atomic and exclusive
- **Consistent Reads**: Read locks ensure readers see a consistent state
- **No Race Conditions**: Write locks prevent readers from seeing partial updates
- **Memory Visibility**: Read-write locks provide proper memory barriers

## Part 4: Mutex, Insert Parallelization [20 Points]

### Situation Where Multiple Insertions Can Happen Safely

**Short Answer:**

**Multiple insertions can happen safely when they target different buckets.**

**Detailed Explanation:**

#### Hash Table Bucket Structure

The hash table uses **buckets** to organize entries:
- Each key is hashed to determine which bucket it belongs to: `bucket_index = key % NUM_BUCKETS`
- There are `NUM_BUCKETS` (5) independent buckets
- Each bucket is a separate linked list stored in `table[0]`, `table[1]`, `table[2]`, etc.

#### Why Different Buckets Enable Parallel Insertions

1. **Independent Data Structures**:
   - Each bucket is a completely separate linked list
   - Modifying `table[0]` does not affect `table[1]`, `table[2]`, etc.
   - No shared memory locations between different buckets

2. **No Race Conditions**:
   - Thread A inserting key X into bucket 0: modifies only `table[0]` and its linked list
   - Thread B inserting key Y into bucket 1: modifies only `table[1]` and its linked list
   - These operations are completely independent - no shared data structures

3. **Per-Bucket Locking Enables Parallelism**:
   - If we use one lock per bucket, threads can acquire locks on different buckets simultaneously
   - Thread A: locks bucket 0, inserts → modifies `table[0]`
   - Thread B: locks bucket 1, inserts → modifies `table[1]` (can happen in parallel with A)
   - Thread C: locks bucket 0, waits for A (same bucket, must serialize)

#### Example Scenario

With 8 threads inserting keys:
- Thread 0: key 0 → bucket (0 % 5) = **bucket 0**
- Thread 1: key 1 → bucket (1 % 5) = **bucket 1**
- Thread 2: key 2 → bucket (2 % 5) = **bucket 2**
- Thread 3: key 3 → bucket (3 % 5) = **bucket 3**
- Thread 4: key 4 → bucket (4 % 5) = **bucket 4**
- Thread 5: key 5 → bucket (5 % 5) = **bucket 0** (same as thread 0)
- Thread 6: key 6 → bucket (6 % 5) = **bucket 1** (same as thread 1)
- Thread 7: key 7 → bucket (7 % 5) = **bucket 2** (same as thread 2)

**Parallelizable insertions:**
- Threads 0, 1, 2, 3, 4 can insert **simultaneously** (different buckets)
- Threads 5, 6, 7 must **wait** for threads 0, 1, 2 respectively (same buckets)

#### Why This is Safe

1. **No Shared Memory**: Different buckets use completely different memory locations
2. **Independent Operations**: Modifying one bucket doesn't affect others
3. **Proper Locking**: Each bucket has its own lock, so operations on different buckets don't interfere

### Changes Made: `parallel_mutex_opt.c`

The `parallel_mutex_opt.c` **already implements per-bucket locking**, which enables parallel insertions to different buckets.

#### What Makes It Work

1. **Per-Bucket Locks**:
```c
pthread_rwlock_t bucket_locks[NUM_BUCKETS];  // One read-write lock per bucket
```

Instead of a single global lock, we have **one lock per bucket**. This allows:
- Threads operating on different buckets to acquire different locks
- True parallelism for insertions to different buckets

2. **Bucket-Specific Locking in `insert()`**:
```c
void insert(int key, int val) {
  int i = key % NUM_BUCKETS;  // Determine which bucket
  // ...
  pthread_rwlock_wrlock(&bucket_locks[i]);  // Lock ONLY this specific bucket
  // ... modify table[i] ...
  pthread_rwlock_unlock(&bucket_locks[i]);
}
```

**Key points:**
- Each insertion locks **only the specific bucket** it's modifying
- Different buckets use different locks, so they can be locked simultaneously
- Threads inserting into the same bucket serialize (correct behavior)

3. **Initialization of Per-Bucket Locks**:
```c
// Initialize read-write locks for each bucket
for (i = 0; i < NUM_BUCKETS; i++) {
    if (pthread_rwlock_init(&bucket_locks[i], NULL) != 0) {
        panic("read-write lock initialization failed");
    }
}
```

Each bucket gets its own independent lock.

#### Comparison: Single Lock vs Per-Bucket Locks

**Single Global Lock (original `parallel_mutex.c`):**
```c
pthread_mutex_t table_lock;  // ONE lock for entire table

void insert(int key, int val) {
    pthread_mutex_lock(&table_lock);  // All threads compete for same lock
    // ... modify table ...
    pthread_mutex_unlock(&table_lock);
}
```
- **Problem**: All insertions serialize, even to different buckets
- **No parallelism**: Only one insertion at a time, regardless of bucket

**Per-Bucket Locks (`parallel_mutex_opt.c`):**
```c
pthread_rwlock_t bucket_locks[NUM_BUCKETS];  // ONE lock per bucket

void insert(int key, int val) {
    int i = key % NUM_BUCKETS;
    pthread_rwlock_wrlock(&bucket_locks[i]);  // Lock only this bucket
    // ... modify table[i] ...
    pthread_rwlock_unlock(&bucket_locks[i]);
}
```
- **Solution**: Insertions to different buckets can run in parallel
- **Parallelism**: Up to 5 insertions simultaneously (one per bucket)

#### Performance Benefits

**Theoretical Speedup:**
- **Single global lock**: Maximum 1 insertion at a time
- **Per-bucket locks**: Up to 5 insertions at a time (one per bucket)
- **Theoretical speedup**: Up to 5x for insert phase

**Actual Performance:**
The actual speedup depends on:
1. **Key distribution**: How evenly keys hash across buckets
2. **Thread count**: More threads increase contention on popular buckets
3. **Workload**: Random keys typically distribute evenly across buckets

With random keys and 8 threads:
- **Best case**: All 5 buckets used simultaneously → ~5x speedup
- **Average case**: Some buckets more popular → ~3-4x speedup
- **Worst case**: All keys hash to same bucket → 1x (serialized, but still correct)
